# 项目概要与规范

## Summary
模型数量的**scaling**可以提高表现，是现在工业公认的事实。目前的做法为通过管理上下文来使不同的agent产生联系与协作。得益于大语言模型对自然语言的处理能力，这种协作可以通过自然语言构建的**规约**来形成，例如Claude Code的多agent模式，Claude Code Skill，Claude Code内的*Claude.md*，Codex里的*AGENTS.md*。不同模型协作对解决问题能力的提升已经被验证。   

这种现象被发现，但是多智能体协作的问题并没有被深度讨论。对于一个非语言模型的模型，如何使其参与到模型协作中；不同参数大小的语言模型语言能力不一，模型之间的交流是否需要优化；模型总是被被动地调用，可不可以让模型主动参与到任务完成的过程当中？最重要的问题是，这种依托自然语言构建的系统有没有充分发挥模型之间协作的能力？我认为答案显然是否定的。

**MARVIS**的任务就是回答这些问题。我们的目的用一句话概括就是：深度探索多智能体协作的方案。

本质上，2025年通过RLVA训练的CoT也可以用这种理论解释。大语言模型可以通过生成更长的思考过程来提高性能，比喻成人脑的活动，就是大脑不同区域的活动形成一个序列最后得出结果（逻辑）；在RLVA训练的CoT里，大语言模型充当了大脑的各个部分。那么相同地，如果把思考中的各个部分替换成不同模型的，质量更高又不失任务整体性的输出，最后的结果会不会更好。想象你在要求大模型给你讲一道题的时候，科学计算是由一个可以使用python工具的计算模型完成的，步骤推导是由带逻辑验证器的逻辑模型完成的，最后由适合讲解的语言模型生成对你的讲解。如果这种思考有一个中心的话，把这种中心替换成进行科研工作的工作者，个人在科研中的作用会被如何放大。

这种协作可以通过单一*中心模型*的统一调度完成吗？看起来，有一个中心的purpose，所有模型的的协作会一致。我认为这种做法有两种困难：1.*中心模型*对工具模型的利用能力不是通用的，也就是说按照现有的方法，我们不可能训练出一个模型可以熟练地，optimally控制以前的、现在的、未来会出现的模型。2.想要optimal的模型协作，现在的做法是scale模型的参数大小。随着更多的应用、更多的模型出现，参数会越来越大，针对任务的*微调*会越来越困难。按照我目前的想法，我们可以在**MARVIS**中做以下尝试：假设模型的协作存在某种自然规律，通过多智能体强化学习训练出一种系统结构，使得这种结构可以让智能体有*逻辑*地协作；每个模型（应用）都有自己的善于操作自身的Head Model，可以在系统中主动地使用本身的模型，并遵循系统整体任务逻辑。

(Till now the idea above is *personal*, and not verified, and stays alterable.)

对于项目名称中的‘操作系统’，其实和计算机操作系统有很大区别。这个名字主要是强调我们具体实现我们的方法，解决实际的问题。

## Rules
### On Large Language Models (!Vibe Coding)
原则上，核心代码**不允许**使用大模型生成（除UI代码）。也不鼓励*任何问题*都询问大模型尤其是*任何问题*的*解决方案*。

使用大模型学习概念永远要放到最后一位，我们应该首先查找论文，查找书籍，查找论坛。一旦大模型参与到我们对项目的方向把握之中后期维护以及新想法的产生都会很困难！

### On Agenda
期末考试结束后我们就进入项目进行阶段。尤其假期可能要麻烦大家投入更多精力。我们的队伍小，可以一周两次小会（十几分钟），一个月一大会。

### On Cooperation
由于队伍较小，我一般习惯大家抱团研究，从一个问题移动到下一个问题。
